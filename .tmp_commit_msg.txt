feat(v8.15): 任务分级超时——慢任务单独放宽，实时链路维持紧超时

改了什么:
- backend/config.py：新增 LLM_TASK_TIMEOUTS 属性（LLM_TASK_TIMEOUTS，JSON 对象，
  值为秒数，如 {"report":180,"career":180}）。解析口径与 LLM_TASK_MODELS 同构：
  未知任务名/非数值/非正数跳过并告警，坏 JSON 整体忽略；未配置任务沿用
  LLM_TIMEOUT（向后兼容，不配即无变化）
- backend/llm_client.py：新增 resolve_task_timeout(task)——任务覆盖优先，否则
  全局 LLM_TIMEOUT。四条调用链（同步 chat / chat_json / 同步流式 / 异步流式）
  全部在 fallback 循环里按当前任务的分级值经 create() 的**按请求参数**下发——
  OpenAI SDK 支持按请求覆盖客户端缺省，构造时烤死的全局值只作缺省，
  无需为超时重建或缓存任何客户端。与任务级模型绑定的关系：绑定换的是
  "用哪个模型"，分级超时换的是"等多久"
- tests/test_task_timeouts.py（新增 13 条）：解析验证 7（未知任务/非数值/
  非正数/坏 JSON/非对象）、resolve 2、端到端 4——直接断言 create() 收到的
  timeout 值，含证伪锚点（改 env 里任务超时，落到 SDK 的值必须跟着变；
  把按请求下发改回"只在构造时设置"本文件即红）
- .env.example：分级超时说明（置于 LLM_TIMEOUT 与任务绑定两节之间）
- 文档：CHANGELOG v8.15 段（v8.0 → v8.15）；LIMITATIONS 对应行更新
  （任务分级已补，"WS 单轮总预算"保持独立登记未做）

为什么改: v8.10 的 LLM_TIMEOUT 是全局上限——报告/职业规划这类长 prompt +
长输出的慢任务 60s 常常不够，此前只能整体调大，等于给实时链路也放开了等待
上限（挂起更久才触发 fallback 换候选）。本轮按 LIMITATIONS 登记的演进方向，
复用 v6.2 任务级模型绑定的注册表思路补上分级超时；范围纪律维持：
"WS 侧单轮总预算"约束的是一轮对话中多次模型往返的累计时长，与本轮的单请求
超时是两层，独立登记不混做。
