项目前备知识_决策过程记录.md

AI模拟面试官项目 —— 前备知识与决策过程记录

本文档整理了项目选题到框架确定的完整决策链路，供开发时理解"为什么这么设计"，也作为AI协作过程材料的依据之一。

一、项目背景

本项目属于重庆大学大数据与软件学院《AI4SE实训一》课程作业。课程核心考核逻辑是"不考手工编码速度，考与AI协同的深度与质量"，AI交互日志是重要评分依据。项目案例分三档难度：基础级(0.9)、标准级(1.0)、挑战级(1.1)，最终成绩会乘以难度系数。

评分构成：知识补强(10) + 平时表现(15) + 作业练习(15) + 项目验收答辩(60，其中AI协作占20分：批判性思维10+协作过程10) × 难度系数。

二、选题决策全过程

2.1 初始方向探索

最先考虑的是挑战级(1.1)清单中的5个项目：多模态中草药识别、漫画多语言翻译、有声读物生成、独居老人安全检测与陪护、Roguelike游戏。经过对比，"个性化有声读物智能生成"因为是纯API编排型项目（情感分析→TTS→背景音乐匹配），工作量可控但演示效果花哨，一度被作为首选推荐。

2.2 转向"AI模拟面试官"

用户提出有声读物"没有实际使用价值"，转向标准级(1.0)的"AI模拟面试官"。经对比分析：

  • 有声读物涉及音频+情感匹配等多模态环节，现场演示时任何违和感（如BGM情绪不匹配）会被评委直接感知，属于"不需要追问就会暴露"的硬伤
  • AI模拟面试官核心链路是纯文本对话（简历解析→大模型→文本反馈），没有音频/图像这种直接可感知的输出形式，输出质量即使一般也很难在现场被一耳朵听出问题
  • 结论：面试官项目的失败模式更隐蔽，健壮性更高，即使技术含量本身不算深

2.3 已有项目的复用尝试与否决

用户提出已完成一个"招聘数据分析与可视化系统"项目（job-crawler），技术深度远超基础级(0.9)要求，包含Playwright爬虫、KMeans聚类、双Agent简历审查（Critic诊断+Optimizer重写）、LLM双模型fallback、250个测试用例、Docker部署、CSRF/限流等安全加固。

该项目最终被否决直接复用，原因有二（均为硬性风险，非技术问题）：

  1. 该项目已交过其他课程作业 —— 若原样复用于本次实训，构成学术诚信风险（同一成果重复提交），一旦查重会被认定为不端行为，而非单纯"技术水平不够"
  2. 开发过程中与AI的对话记录已清空 —— 无法举证评分表要求的"AI协作过程"20分，且事后无法安全补救（伪造记录风险更高）

结论：不能直接复用代码或数据，但可以复用架构设计经验（如双Agent职责分离、LLM调用fallback机制的设计思路），因为设计思路本身不构成查重风险，代码需要在本次实训期间重新实现。

2.4 系数纠结与"以面试官为主体，数据分析为支撑模块"的定位

用户一度纠结0.9系数"太吃亏"，考虑过将"招聘数据分析"与"AI模拟面试官"合并为自定义组合选题，但该做法存在规则风险：课程案例清单未提及允许自由组合，系数认定需老师额外判断，存在"两头不讨好"的风险（数据分析不够深、面试官不够专注）。

最终明确定位：项目本质仍是1.0难度的"AI模拟面试官"，招聘数据分析不是独立并列模块，而是面试官项目内部的一个可选支撑功能（用于让生成的面试问题有真实岗位数据依据，避免大模型凭空编造技能要求）。系数按1.0计算，无需额外认定。

由此产生两条硬性约束：

  • 若做数据支撑模块，数据必须重新采集，不能直接复用job-crawler已有的data.db（同一批数据资产复用同样构成查重风险）
  • 数据支撑模块深度要克制，只做"岗位关键词→技能要求速查"级别的简单查询接口，不做聚类、热力图、相似度网络等高阶分析功能（那是job-crawler为了单独撑起0.9项目而做的，此处角色不同，不需要重复堆砌）

2.5 第一性原理重新审视项目本质

对"AI模拟面试官"做第一性原理拆解，得到以下关键结论：

  1. 面试表现差的根本原因分三类：不知道会被问什么（信息缺失）/ 知道但回答质量差（表达结构化能力缺失）/ 临场心理状态问题。本项目选择主攻第二类。
  1. "面试官"是一种产品包装，不是必然逻辑——问问题（需要理解岗位、设计追问路径）和给反馈（需要评估回答质量）是两种不同能力，可以拆解为独立模块而非强行捆绑成一个拟人化角色。
  • 问题生成——不用大模型也能做到八成（题库+规则库），大模型的增量价值仅在于"针对具体简历/JD个性化"，属于锦上添花，不值得投入过多精力
  • 回答质量诊断——大模型不可替代（"逻辑是否清晰"难以规则化判断），是项目真正的核心价值所在
  1. 大模型必要性检验：
  1. 最终建议：资源向"回答质量诊断引擎"倾斜（占开发精力60%以上），问题生成模块做轻做浅，数据支撑模块先做最小实验验证必要性，不默认它是必需的。

三、被否决的方案汇总（避免重复踩坑）

| 方案 | 否决原因 | |---|---| | 有声读物生成(1.1) | 多模态输出（音频+音乐匹配）现场演示违和感容易被直接感知，健壮性风险高于面试官 | | 独居老人陪护(1.1) | 需要硬件/嵌入式基础，用户完全没有相关经验，job-crawler的Agent架构经验也无法复用到硬件层 | | 中草药识别(1.1) | 技术栈（图像分类+知识图谱）与已有的job-crawler经验（纯后端+NLP+Agent）不重叠，复用价值低 | | 直接复用job-crawler项目 | 已交过其他课程（查重/学术诚信风险）+ AI交互记录已清空（无法举证协作过程分） | | 招聘数据分析+AI面试官自定义组合 | 课程规则未明确允许自由组合选题，系数认定存在不确定性，且容易显得"硬拼凑" | | 面试官项目功能堆砌（历史追踪/多语言/语音输入） | 第一性原理检验下，这些功能"有没有AI都差不多"或不解决核心问题，属于稀释核心亮点的边角料 |

四、最终确定的项目方向

项目名称：AI模拟面试官（回答质量诊断为核心） 难度系数：1.0（标准级） 核心定位：不是"像不像面试官"，而是"能不能像犀利教练一样精准诊断回答质量" 详细架构：见配套文档《AI面试官_核心框架.md》

五、给codebuddy的开发要求提醒

  1. 所有代码需在本次实训期间原创实现，不得复用job-crawler仓库的任何代码或数据文件
  2. 如需实现数据支撑模块，须使用新采集或手动整理的小型静态数据集
  3. 诊断引擎须采用双Agent职责分离设计（Diagnostician只诊断，Rewriter只改写），避免自评式循环验证的逻辑漏洞
  4. 开发过程中每一轮需求确认、bug修复、prompt调优都应形成可追溯的对话记录，用于后续AI交互日志整理

AI面试官_核心框架.md

AI模拟面试官 —— 核心框架设计文档

一、产品定位

核心价值不在"像不像面试官",而在"能不能像犀利教练一样精准诊断回答质量"。

全部资源向"回答质量诊断引擎"倾斜，问题生成模块做轻做浅，不做数据支撑模块（除非最小验证证明必要）。

二、系统架构（三层）

┌─────────────────────────────────────────┐
│              前端交互层                    │
│   简历/JD上传 → 对话界面 → 诊断报告展示        │
└─────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────┐
│              业务逻辑层 (核心)              │
│  ┌───────────────┐  ┌──────────────────┐ │
│  │  问题生成模块    │  │  回答诊断引擎(重点) │ │
│  │  (轻量单Agent)  │  │  (双Agent协作)     │ │
│  └───────────────┘  └──────────────────┘ │
└─────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────┐
│              基础设施层                    │
│   简历解析(PDF/DOCX) + LLM调用封装(fallback)│
│   + 会话状态存储(SQLite)                   │
└─────────────────────────────────────────┘

三、核心模块详细设计

3.1 回答质量诊断引擎（核心，占开发精力60%以上）

采用双Agent协作模式（复用你在job-crawler里验证过的Critic+Optimizer思路）：

用户回答文本
    ↓
┌─────────────────────────┐
│  Diagnostician Agent     │  职责：只诊断，不给答案
│  （诊断者）                │  输出结构化问题清单
└─────────────────────────┘
    ↓ 诊断结果
┌─────────────────────────┐
│  Rewriter Agent          │  职责：基于诊断结果，给出
│  （改写者）                │  具体修改示范（不是泛泛建议）
└─────────────────────────┘
    ↓
结构化诊断报告

诊断维度（固定4个，不要贪多）：

  1. STAR完整度 —— 情境/任务/行动/结果是否齐全，缺哪个明确指出
  2. 量化程度 —— 是否有具体数字支撑（"提升了效率"vs"效率提升30%"）
  3. 逻辑连贯性 —— 前后是否有因果断层
  4. 岗位相关性 —— 回答内容是否切中该岗位真正关心的能力点

输出格式（务必结构化，不要让大模型自由发挥输出一段话）：

{
  "star_check": {"missing": ["Result"], "comment": "..."},
  "quantification": {"score": 2, "suggestion": "..."},
  "logic_gaps": ["第二句到第三句之间缺少因果说明"],
  "relevance": {"score": 4, "comment": "..."},
  "rewritten_example": "改写后的示范回答（150字内）"
}

为什么这样设计是"AI协作深度"的加分点：

  • Diagnostician和Rewriter职责分离，避免"一个Agent既当裁判又当运动员"的自评式漏洞（这正是之前分析中AI模拟面试官最大的技术硬伤，现在用架构设计解决掉）
  • 结构化输出让"批判性思维"可举证——你可以在AI交互日志里展示"我发现诊断结果里逻辑断层判断不准，于是调整了prompt"这类真实迭代记录

3.2 问题生成模块（做轻，单Agent即可）

简历文本 + JD文本
    ↓
关键词提取（大模型一次调用，不需要额外NLP处理）
    ↓
生成5-8道针对性问题（一次性生成，不做复杂的动态追问树）

不做的事：多轮动态追问逻辑、追问路径规划——这些复杂度收益比低，第一性原理已验证增量价值有限。

3.3 数据支撑模块（先验证，后决定）

做之前先跑这个最小实验：

  1. 挑3个岗位（如Python开发、产品经理、数据分析），不接任何外部数据，直接让大模型生成面试问题
  2. 你自己判断：问题是否脱离实际、是否有编造的技能要求
  3. 如果问题质量合格 → 砍掉这个模块，减少工作量和查重风险
  4. 如果确实有明显编造/过时问题 → 只做一个极简版本：给定岗位关键词，返回3-5条真实技能要求（可以是你手动整理的小型静态数据集，不需要重新做爬虫，规避复用job-crawler数据的风险）

四、技术栈建议

| 层级 | 技术选型 | 理由 | |---|---|---| | 后端框架 | Python + FastAPI | 轻量，codebuddy生成效率高 | | LLM调用 | 单一大模型API（DeepSeek或其他），做简单try-except fallback | 不需要双模型，面试官场景对模型能力要求没那么极端 | | 简历解析 | PyPDF2 / python-docx | 成熟方案，直接抄job-crawler的resume_parser思路即可（代码可以重写，逻辑可以参考） | | 数据存储 | SQLite | 存会话记录、诊断历史 | | 前端 | 简单HTML+JS或React（视时间而定） | 优先把诊断报告的可读性做好，不需要花哨UI |

五、给codebuddy的任务拆解顺序

  1. 第一轮：让它产出需求文档+架构设计文档，你重点审查诊断维度设计是否合理、Agent职责划分是否清晰
  2. 第二轮：先做诊断引擎（核心），用几段你自己写的模拟回答测试效果，反复调prompt——这一步的调试过程就是你的AI交互日志主体
  3. 第三轮：做问题生成模块（轻量，一两天内应该能完成）
  4. 第四轮：决定要不要做数据支撑模块（按上面3.3的验证结果）
  5. 第五轮：前端串联+联调

六、答辩时的核心叙事（提前想好）

一句话讲清楚项目价值："市面上的面试模拟工具大多停留在'问问题'，我们的核心创新是把重心放在'精准诊断回答质量'——用双Agent分离诊断与改写职责，避免AI自己既当裁判又当运动员的自评漏洞。"

这句话直接把之前分析里"自评式架构不严谨"的风险点，转化成了你的技术亮点和批判性思维证据。

CODEBUDDY.md

AI模拟面试官

本文档是 CodeBuddy 的项目记忆文件，每次新对话自动加载。请在接手本项目时严格遵循以下规范。

项目概览

核心价值：回答质量诊断，不是"像不像面试官"。资源优先级：

  1. 诊断引擎（Diagnostician + Rewriter 双Agent）— 核心，占开发精力 60% 以上

技术栈：Python 3.12 / FastAPI / SQLite (aiosqlite) / DeepSeek API (OpenAI 兼容) / 原生 HTML+JS 前端

架构约束（必须遵守）

双 Agent 不可合并

Diagnostician + Rewriter 是两个独立 Agent，禁止合并为单一 Agent。诊断和改写必须分步进行，各自有独立的 prompt。

诊断四维度

诊断始终围绕四个维度评分：

  1. STAR 完整性
  2. 量化程度
  3. 逻辑连贯性
  4. 岗位相关性

范围纪律

  • 禁止在未经用户明确批准的情况下新增功能模块（如语音、多面试官切换、历史趋势追踪等）
  • 如认为某功能确有必要，只能以建议形式提出并等待用户批准，不得直接实现
  • 例外（无需额外批准即可做）：对现有 4 个诊断维度的参数化优化，例如按 JD 动态调整评分权重、增加"回答过短触发追问"这类轻量规则

开发纪律

模块开发前

每个功能模块开始前，先输出需求理解文档，存入：

docs/weekN_模块名_需求.md

内容包含：模块目标、技术方案、涉及的知识点。

修改迭代时

用户提出修改意见后，在对应需求文档里追加一段：

## 修改记录 [日期]
- 原方案：...
- 用户指出的问题：...
- 修改后的方案：...

这是评分中"批判性思维"分项的核心证据，必须真实、具体，不能用"优化了逻辑"这种空泛表述。

Commit Message 规范

禁止使用"fix bug"、"优化代码"等空泛描述，必须写清楚：

改了什么: ...
为什么改: ...

变更前复述

用户指出问题后，须先复述问题本质，确认理解无误后再给出修改方案，不得跳过复述直接改代码。

周报

每周五（或用户指定的开发节点）自动生成周报，存入：

docs/weekN_周报.md

项目收尾

项目开发结束前，自动汇总所有需求文档和周报，按时间线整理成一份完整的《AI协作过程记录》：

docs/AI协作过程记录_完整版.md

边界声明

以下事项由用户本人负责，AI 只记录决策结果：

  • 诊断维度的设计取舍
  • 是否开发数据支撑模块
  • 项目范围的增减

  • 禁止在未经用户明确批准的情况下新增功能模块（如语音、多面试官切换、历史趋势追踪等），哪怕参考项目中存在类似功能

3.4 变更留痕纪律

  • 每次代码修改需说明"改了什么 + 为什么改"，禁止使用"优化了逻辑""修复了问题"等空泛描述
  • 用户指出问题后，须先复述问题本质，确认理解无误后再给出修改方案，不得跳过复述直接改代码
