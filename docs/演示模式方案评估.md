# 演示模式方案评估（v6.4 候选 / 待批准）

> 来源：《[MockFlow-深度研读.md](MockFlow-深度研读.md)》§2「双运行模式」与 §10 P1-1 建议。
> 性质：**方案评估文档，未实施**——演示模式属新增功能模块，按 CHARTER 范围纪律须用户批准后才动工。
> 日期：2026-08-29　基线：v6.3（P2 两项已于本日落地）

---

## 1. 问题定义

**现状**：`llm_client.py` 模块级实例化，环境无可用 LLM API Key 时：

1. 后端多个模块 **import 即失败**，服务无法启动；
2. 全量测试套件**收集阶段就失败**（CHARTER 测试策略已披露此局限）；
3. 答辩/演示必须依赖 Key + 网络可达 + Provider 可用三个条件同时成立。

**MockFlow 的启示**：它的三级兜底（确定性 API → 前端本地兜底 → 流程永不中断）保证"任何人任何时刻打开都能看到完整闭环"。我们的引擎质量远高于它，但演示可用性为零——这是唯一被它反超的维度。

**目标**：同一套协议（WebSocket 消息 / REST 路由）下，提供一条**确定性引擎**降级路径，使无 Key、弱网环境下产品仍可完整走通"出题 → 回答 → 诊断 → 追问 → 报告"闭环，且**不冒充 LLM 诊断**（诚实原则）。

---

## 2. 现成零件盘点（演示引擎不需要从零造）

关键判断：**v5.0→v6.3 的竞品借鉴已经把确定性演示引擎的全部零件造好了**，且全部是零 LLM 的纯函数/数据：

| 演示链路环节 | 现成零件 | 所在层 | 状态 |
|---|---|---|---|
| 出题-题源 | `question_bank`（题库） | L3 | ✅ 现成 |
| 出题-压力题 | `pressure_bank`（16 道，含三道闸门 `_maybe_inject_pressure`） | L2/L3 | ✅ 现成 |
| 出题-方向 | `resume_anchors.classify()`（关键词五分类） | L2 | ✅ 现成 |
| 出题-缺口 | `gap_analyzer` 的 LLM 路径不可用，退化为**无缺口模式**（v6.3 已支持 `jd_gaps=[]` 降级） | — | ✅ 已支持 |
| 诊断-加减分 | `score_adjustments.detect_adjustments()`（10 条正则规则，带 evidence） | L2 | ✅ 现成 |
| 诊断-证据 | `resume_retriever` / `knowledge_store`（双通道检索，v6.4 已补 bigram 通道） | L2 | ✅ 现成 |
| 追问 | 角色卡 `followup_chain`（纯数据）+ 规则最低分维度 | L1 数据 | ✅ 现成 |
| 收尾/推进 | 轮次计数 + `is_closing_round()` + `min_questions`（纯工程逻辑） | L3 | ✅ 现成 |
| 报告 | `build_report` 消费诊断结果，不关心分数从哪来 | L3 | ✅ 现成 |
| 输出净化 | `output_sanitizer`（纯函数） | L2 | ✅ 现成 |

**缺口只有一个**：诊断引擎的"基础五维分"目前只能由 LLM 产出；`score_adjustments` 只做加减修正，没有基础分。演示模式需要一个新的**规则版基础分函数**（约 60~100 行，纯正则/阈值：STAR 完整度按要素词命中、量化程度按数字密度、逻辑按分句结构、岗位相关按 JD 词命中、深度按领域词表），全部可单测。

## 3. 备选方案对比

### 方案 A：完整演示模式（全链路确定性引擎）

`AI_DEMO_MODE=auto|on|off`（auto = 无 Key 自动进入）。`llm_client` 改为延迟/可选实例化；`question_gen` / `diagnosis_engine` 内部按模式分流到确定性管道；WS 协议与 REST 路由不变，每条消息带 `engine: "demo" | "llm"` 标记。

- **优点**：演示/答辩零外部依赖；测试收集解除 Key 依赖；与 v4.3 Provider 降级链自然衔接为最后一级。
- **缺点/风险**：
  - **llm_client 可选化是最大工程量与风险点**——模块级实例化散布在 import 链上，需逐个改为惰性获取；
  - **双引擎漂移风险**（正对《MockFlow-深度研读.md》§4.3 的 TS/Py 双写教训）：同一语义在 LLM prompt 与规则函数各写一份，改一处忘一处。缓解：规则版只复用 L2 零件、参数全部收口 `config.py`、测试矩阵按"每条消息类型 × 两种引擎"组织；
  - 诊断质量差距是**本质性的**，必须在报告里显式标注 `engine: demo`（"本报告由确定性规则引擎生成，仅演示数据链路，不代表 LLM 诊断能力"），否则构成对评分能力的虚假陈述。
- **工程量估算：3~5 人日**（llm_client 惰性化 1 天；demo 出题管道 1~1.5 天；demo 诊断基础分 1~1.5 天；测试 + lint + 文档 1 天）。

### 方案 B：仅修复"无 Key 不可用"（启动降级报错 + 测试收集修复）

不动引擎：`llm_client` 惰性化后，无 Key 时服务可以启动，但创建会话/诊断时返回**明确的引导性错误**（"未配置 API Key，无法进行 LLM 诊断；演示模式开发中"）。

- **优点**：半天工作量；立刻解除测试收集的 Key 依赖（CI/评分环境友好）；零漂移风险。
- **缺点**：演示可用性仍是零——只把"崩溃"变成"优雅的不可用"。
- **工程量估算：0.5 人日**。

### 方案 C：前端静态演示壳（MockFlow 式假数据兜底）

**否决**。用硬编码数据伪造报告/历史正是《MockFlow-深度研读.md》§7 批判的反面教材：答辩追问"这个分数怎么来的"即穿帮，违背 CHARTER 诚实披露原则。演示数据可以存在，但必须显式标注"示例数据"，且不得进入真实会话流。

### 推荐

**B 先行（v6.4 内顺手完成），A 立项为 v6.5 候选**。理由：B 是 A 的前置（llm_client 惰性化是 A 最重的活，B 先把这一步做掉并单独验证）；A 的增量（demo 出题/诊断管道）是纯新增代码，随时可接；先小后大，避免一个 3~5 人日的改动与 v6.4 其他内容混在一起难以回退。

## 4. 方案 A 落地设计（若批准，按此执行）

### 4.1 配置（`config.py`，L1）

```python
# AI_DEMO_MODE: auto(无 Key 自动进入) / on(强制) / off(禁用，无 Key 保持报错)
DEMO_MODE = os.getenv("AI_DEMO_MODE", "auto")   # 校验取值，非法回退 auto
```

### 4.2 llm_client 惰性化（L1，风险最高的一步）

- 模块级 `llm_client = LLMClient()` 改为 `get_llm_client()`（带缓存的工厂函数）+ 兼容别名；Key 缺失时实例返回 `available=False` 而非抛异常；
- 逐个排查 import 链上的模块级使用点（`diagnosis_engine`、`question_gen`、`career_planner` 等），改为调用点获取；
- 验收标准：`.env` 无 Key 时 `python -m pytest tests/ -q` 全量收集成功（新增前置校验用例）。

### 4.3 demo 出题管道（L3）

```
锚点分类(resume_anchors.classify) → 按 JD/锚点类别从 question_bank 选题
→ 压力题三道闸门(复用 _maybe_inject_pressure) → 换题去重(asked_question_hashes)
→ 语气套用面试官风格(纯模板前缀)
```

与 LLM 路径共享：去重机制、压力闸门、轮次推进、收尾强控（这些本来就是工程层）。

### 4.4 demo 诊断函数（L3）

规则版基础五维分（正则/阈值，全部可单测）+ `score_adjustments` 加减分 + `weighted_score` 加权（现有数学层原样复用）。产出结构 = 现有诊断 schema，另带 `engine: "demo"` 字段贯穿到报告。

### 4.5 诚实性护栏（硬约束）

1. WS 每条消息与报告均携带 `engine` 字段，前端题目卡/报告页渲染"规则引擎演示"徽章；
2. README / CHARTER 披露"演示引擎不评估诊断质量，诊断有效性验证仅针对 LLM 路径"；
3. 演示模式不写入 `dimension_weights` 的 LLM 推断来源标记（`weight_source` 必须如实标 `demo`）。

### 4.6 验收清单

- [ ] 无 Key 环境全量测试收集通过；
- [ ] 无 Key 环境 WS 完整走通出题→回答→诊断→追问→报告，消息均带 `engine: demo`；
- [ ] `AI_DEMO_MODE=off` 时行为与现状完全一致（回归）；
- [ ] `python run.py lint` 通过（新增模块登记 L2/L3 契约）；
- [ ] 演示模式诊断分与 LLM 诊断分在同一测试集上的差异幅度有文档记录（披露用）。

## 5. 决策点（需用户确认）

1. **是否批准方案 A**（立项 v6.5）？或仅做方案 B？
2. 演示模式在答辩中的叙事定位：作为"工程完备性"卖点（同一协议多引擎），还是仅作为"可用性兜底"低调披露？
3. demo 诊断是否需要**支持追问**（按规则最低分维度生成模板追问）？不支持则演示闭环缺"动态追问"环节，支持则 demo 管道多约 0.5 人日。建议：支持，追问是产品叙事的核心环节。

## 6. 第一性原理审视（2026-08-29 补充，**结论：A 否决、B 值得做**）

> 本节回答用户问题："从第一性原理出发，有必要改造这个演示模式吗？"结论推翻 §3 的"A 立项 v6.5"建议。

### 6.1 逐层检验

1. **演示模式解决的是什么问题？** "无 Key 时不能演示"——这是**可用性**问题，不提升诊断内核质量一寸。
2. **演示的真实场景是什么？** 课程项目的答辩场景 = 本人与自己的 Key 与网络，不是发布给无 Key 用户的 To C 产品。唯一真实硬需求是"评分者 clone 后能跑起来"——方案 B（不崩 + 明确报错 + README 说明）即可 100% 覆盖，不需要 A 的 3~5 人日。
3. **A 的真实代价？** 不止一次性 3~5 人日，还有**永久的双引擎税**：每次改锚点/评分规则/题库都要同步维护 LLM prompt 与规则函数两份语义（即本评估 §3 警告、MockFlow 研读 §4.3 实证的漂移问题）。为低频场景缴永久税，得不偿失。
4. **MockFlow 为什么需要、我们为什么不需要？** 它的引擎本来就是确定性的，Demo API 就是它的真产品；我们做演示模式等于造一个"**不能诊断的诊断引擎**"——影子产品。答辩被追问"演示模式的诊断准吗"时只能答"不准"，自造软肋、稀释核心卖点。
5. **项目自己的宪章怎么判？** CHARTER 范围纪律对认证/HTTPS 的判词："经第一性原理评估均不提升诊断内核质量，属产品化/上云阶段事项"。演示模式完全落在同一条判词里，答案由项目自身决策逻辑给出。

### 6.2 结论与翻案条件

- **方案 A：否决**，不再立项。本节即为决策记录。
- **方案 B：同样否决（缓议）**，见 §6.3。
- **翻案条件**：将来若公开部署给无 Key 用户、或课程要求他人离线复现完整流程（产品化阶段），再评估 A——届时 B 已完成 llm_client 惰性化，A 的增量随时可接。

### 6.3 B 也否决：前提塌了，结论必须重推（2026-08-29 二次修正）

> §3 的"B 先行"建议是从"A 立项 v6.5"这个前提推出来的（B 是 A 的前置）。A 否决后前提不成立，B 必须重新推导而非沿用旧结论——此即本节。

B 的三个组成部分逐一检验：

| 组成 | 解决的问题 | 问题对谁真实存在 | 判定 |
|---|---|---|---|
| `llm_client` 惰性化（B 的主体） | 无 Key 时 import 失败 | 只对"无 Key 却要跑测试/启动服务的人"。本人有 Key，全套件实际可跑；该局限已被 CHARTER **诚实披露**（已知且刻意的取舍，非待修 bug） | 收益兑现在假想场景，成本却是 A 全部风险中最高的 import 链改造——**白付最高风险的成本，拿不到 A 的任何收益** |
| 无 Key 启动友好报错 | clone 者不读 README 直接启动的体验 | README 已写明 `.env` 配置步骤 | 锦上添花，非需求 |
| 解除测试收集的 Key 依赖 | 无 Key 环境跑全量套件 | 无 CI、无已知的无 Key 评分环境；测试本就全 mock，Key 依赖属 import 副作用的偶然耦合，但修掉它的收益只在真实出现该环境时兑现 | 同上，假想场景 |

**三判据**：① 不提升诊断内核质量（宪章同款判词）；② 问题只存在于假想场景且局限已披露；③ B 存在理由原是 A 的前置，A 否决即失去理由。**结论：B 现在也不做。**

**B 的翻案条件**（任一真实出现即升格为必要）：
- 出现必须无 Key 跑全量套件的评分/CI 环境；
- 课程要求他人在无 Key 环境复现测试；
- 重启方案 A。

**本评估的最终决策**：A、B 均不做，保持现状（局限已诚实披露于 CHARTER/测试策略）。本节与 §6.1 共同构成完整决策链：提出 → 第一性原理否决 A → 前提重推 → 否决 B → 留翻案条件。P2 两项（已落地）是本轮竞品借鉴的全部产出。
