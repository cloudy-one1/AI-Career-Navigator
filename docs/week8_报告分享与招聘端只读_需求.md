## 1. 模块目标

### 1.1 要解决的本质问题

前两个模块（认证、三实体）都是**为求职者服务的**——让求职者的资产可复用、数据不外泄。但它们没有产生任何"招聘者视角"的东西。

双端平台成立的关键是：**求职者的诊断结果，能不能以求职者可控的方式，给招聘者看？**

注意动词是"给"，不是"被看"。这个区别决定了整个模块的设计方向：

| | 招聘方平台模型（已否决的 B） | 本模块的模型（A） |
|---|---|---|
| 谁发起 | 招聘者建会话，候选人被邀请 | **求职者自己练，主动分享** |
| 权力关系 | 招聘者持有数据 | **求职者持有数据，随时可撤销** |
| 与产品命题的关系 | 推翻"帮候选人变强" | **不变**——分享只是报告的导出方式 |

这个取舍很重要：**保留求职者的数据主权**，是本模块与"照搬招聘方平台"最本质的区别，也是不违背 CHARTER 产品命题的原因。

### 1.2 目标

1. 求职者可为一个会话的报告生成分享链接（可设有效期、可撤销、可看访问次数）
2. 招聘者**免登录**，凭链接只读查看
3. 分享出去的内容按求职者选择**分级披露**（是否含完整问答原文）
4. 敏感信息（手机号/邮箱/身份证）强制脱敏，不依赖求职者选择

### 1.3 非目标（明确不做）

- 不做访问密码（可选增强，有余力再做）
- 招聘端**不能**写任何数据：不能改报告、不能留言、不能下载原始简历
- 不做分享链接的"投递/申请"语义（不是招聘流程，只是报告查看）
- 不做防作弊（切屏/眼神检测）——与"求职者自主练习"的定位冲突，在 DC-06 范围内已明确排除

## 2. 技术方案

### 2.1 数据模型

```sql
CREATE TABLE IF NOT EXISTS share_links (
    token          TEXT PRIMARY KEY,      -- URL-safe 随机 32 字节（secrets.token_urlsafe）
    session_id     TEXT NOT NULL,
    created_by     TEXT,                  -- owner_id（匿名模式为 NULL）
    scope          TEXT NOT NULL DEFAULT 'report_read',  -- 目前只有一种，预留扩展
    include_detail INTEGER NOT NULL DEFAULT 0,           -- 0=仅结论与维度分；1=含逐题问答原文
    expires_at     TEXT,                  -- NULL = 永不过期
    revoked        INTEGER NOT NULL DEFAULT 0,
    access_count   INTEGER NOT NULL DEFAULT 0,
    last_access_at TEXT,
    created_at     TEXT DEFAULT (datetime('now','localtime'))
);
CREATE INDEX IF NOT EXISTS idx_share_session ON share_links(session_id);
CREATE INDEX IF NOT EXISTS idx_share_creator ON share_links(created_by);
```

**为什么 token 要独立随机串而不是 session_id 的哈希**：session_id 会被用在别处（如内存 `active_sessions` 的 key），一旦泄露影响面大于分享范围；独立 token 可以单独撤销而不影响会话本身。

### 2.2 分级披露（核心设计）

求职者生成链接时选择**披露级别**，这个选择一旦做出就落在 DB 里，招聘端无法突破：

| 级别 | 包含内容 | 典型场景 |
|---|---|---|
| `include_detail=0`（默认） | 总分、五维雷达、维度评语、逐题**题目+评分+evidence 引用** | 给 HR 快速判断，不暴露完整回答原文 |
| `include_detail=1` | 上述 + 每道题的**完整回答原文** | 给技术面试官细看 |

**默认 0 是刻意的**：默认最小披露，需要更多是显式选择。这与"求职者持有数据主权"的取向一致。

### 2.3 强制脱敏（不依赖求职者选择）

无论哪个级别，招聘端响应**一律**对以下内容做打码：

| 类型 | 规则 |
|---|---|
| 手机号 | `1[3-9]\d{9}` → `138****8000` |
| 邮箱 | 保留首字符与域名 → `z***@example.com` |
| 身份证 | 18 位 → 保留前 6 后 4，中间 `********` |
| 候选人姓名 | 除创建者自己查看外，一律显示为「候选人」 |

**为什么姓名也要脱敏**：链接可能被转发。招聘方平台（Gua）把候选人姓名直接放报告页，是因为它的链接是定向邀请；我们的链接是求职者自己可能贴到任何地方的，**必须按"可能公开"来设计**。

脱敏实现为一个纯函数 `redact_pii(text: str) -> str`，放在 `backend/auth.py`（L2）还是新建模块？——放 `auth.py` 会让它职责变杂（`auth.py` 是访问控制，脱敏是内容处理）。**决策：新建 `backend/share_access.py` 登记进 L2**，只负责分享令牌与脱敏。

### 2.4 API 设计

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| POST | `/api/sessions/{id}/share` | 需登录 + 是该会话 owner | 生成链接；body 含 `expires_days`（7/30/null）、`include_detail` |
| GET | `/api/sessions/{id}/shares` | 需登录 + owner | 该会话已生成的链接列表（含访问次数、是否有效） |
| POST | `/api/shares/{token}/revoke` | 需登录 + 是创建者 | 撤销（软删除，`revoked=1`） |
| **GET** | **`/api/shared/{token}`** | **免登录** | **招聘端唯一入口**，返回脱敏后的只读报告 |

**免登录端点的风控**：
- token 校验失败/已撤销/已过期 → 一律 404（不返回 403，避免暴露"这个 token 存在但被撤销了"）
- 限流：单 IP 每分钟 20 次（复用现有 `RATE_LIMIT_SESSION` 的量级）
- 每次成功访问 `access_count + 1`，并记录 `last_access_at`

### 2.5 前端

**主应用侧（`report.js` 改造）**：
- 报告页增加"分享"区块：生成按钮、有效期选择、披露级别开关、已生成链接列表（含访问次数、撤销按钮、复制链接）

**招聘端（`share.html` + `shareReport.js`，独立入口）**：
- **不复用主应用外壳**。拿到链接的是外部 HR，不应看到求职者的面试/职业规划/市场数据等私人面板
- 四个区块：
  1. 头部：匿名化称谓 + 应聘岗位 + 完成时间 + "本报告由候选人主动分享"声明
  2. 结论区：总分、五维雷达、录用倾向参考
  3. 逐题证据：题目 + 评分 + 候选人原话引用（脱敏后）
  4. 底部：生成时间、有效期、"本报告为 AI 模拟诊断结果，不构成录用建议"免责声明

设计约束：与既有面板同构的视觉语言（主色 `#2563EB`、卡片化、克制的工程感），但**极简**——无导航、无交互写操作。

## 3. 涉及的知识点

1. **能力令牌（Capability Token）**：把"权限"编码进一个不可猜测的 URL，持有即授权。优点是无状态、免登录；代价是泄露即失守、难以细粒度回收——所以必须配有效期与撤销
2. **默认最小披露原则（Privacy by Default）**：默认给最少信息，需要更多是显式动作。相比"默认全给、让用户关掉"，前者的实际泄露率低一个量级，因为用户几乎不会去关
3. **错误消息的信息泄漏**：token 不存在/已撤销/已过期一律返回 404 而非区分——同样的错误信息无法被攻击者用来枚举有效 token
4. **PII 脱敏的边界**：正则脱敏防不住刻意构造（换分隔符、全角数字、拆字），它是"防意外泄露"而非"防攻击者"。这一点要如实写进 README 已知局限，不能包装成"脱敏保护层"
5. **独立入口的必要性**：分享页不是主应用的一个 tab，因为它的访问者身份完全不同——共用外壳等于把求职者的私人功能暴露给外部人员

## 4. 验证方式

1. `pytest tests/test_share.py -q` 全绿
2. 冒烟：
   - 凭链接可读 → 内容脱敏（手机号/邮箱/姓名已打码）
   - 撤销后再访问 → 404
   - 过期的链接 → 404
   - `include_detail=0` 时响应里**不含**回答原文（断言 `answer` 字段不存在）
   - 招聘端尝试任何写操作 → 无此端点（404）
3. `python run.py lint` 通过（L2 行已登记 `backend.share_access`）

## 修改记录

### 修改记录 2026-08-29（脱敏范围扩大）

- **原方案**：只脱敏手机号/邮箱/身份证，姓名保留——参照招聘方平台（Gua）的做法，报告页直接显示候选人姓名。
- **问题本质**：Gua 的分享链接是**招聘者定向生成、发给特定候选人**的，流转范围可控；而我们的链接由求职者自己生成，**可能被贴到任何公开场合**（论坛、群聊、社交媒体）。把姓名放进一个可无限转发的页面，等于把求职者的身份与其面试表现强绑定公开——这与"帮候选人变强"的产品命题直接冲突。
- **用户判断点**：用户选定的模型 A 明确是"求职者持有数据主权"，那么分享功能的设计前提就必须是"链接可能公开"。
- **修改后的方案**：姓名一律脱敏为「候选人」（创建者自己查看时除外）；并在 §2.3 明确"按可能公开来设计"这一前提。
