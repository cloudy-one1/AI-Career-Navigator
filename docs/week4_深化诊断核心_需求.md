# Week4 · 深化诊断核心（v2.6）需求文档

> 本次迭代不新增"功能面"，而是围绕项目核心价值——**回答质量诊断**——做纵向加深。
> 需求由用户直接提出，共四个方向，均属已批准范围。

---

## 一、模块目标

用户原话：

> 继续深化诊断本身——例如：诊断维度权重按 JD 动态化、追问与诊断流式合并（文档"已知限制"已列）、雷达图实时更新、弱项自动追加针对性题。这些才直接放大核心价值。

拆解为四个目标：

| # | 目标 | 解决的问题 |
|---|------|-----------|
| 1 | 诊断维度权重按 JD 动态化 | 四维等权对所有岗位一视同仁，无法体现"数据岗看重量化、架构岗看重逻辑" |
| 2 | 追问与诊断流式合并 | 追问需二次 LLM 往返，用户干等；且诊断结果一次性弹出，过程不可见 |
| 3 | 雷达图实时更新 | 雷达图只在面试结束后出现，过程中无法感知自己的能力分布 |
| 4 | 弱项自动追加针对性题 | 追加题与原题同质，没有针对薄弱维度补强，追加等于重复 |

## 二、前置问题（实施前发现的既有缺陷）

在动工前对全链路做了核对，发现 **v2.5 拆分引擎时留下的接口断裂**，
这些问题会导致 WebSocket 面试流程直接崩溃，四个新功能都建立在这条链路上，因此必须先修复。

### 2.1 后端接口断裂

`backend/main.py` 的 WebSocket 主流程调用了 `InterviewSession` 上**不存在或签名不符**的方法：

| main.py 调用 | session.py 实际情况 | 后果 |
|-------------|-------------------|------|
| `session.handle_answer()` | 不存在（只有 `record_answer`） | AttributeError |
| `session.should_follow_up(answer, diag)` | 存在但**无参** | TypeError |
| `session.handle_follow_up_answer()` | 不存在 | AttributeError |
| `session.has_more_questions_in_round()` | 不存在 | AttributeError |
| `session.check_round_quality()` | 不存在 | AttributeError |
| `session.advance_round()` 取布尔返回 | 无返回值（None） | 循环判断恒为假 |

### 2.2 安全层返回值误用

`security.full_check()` / `check_output()` 返回的是 **`(bool, str)` 元组**，
但 `main.py` 当作 dict 使用（`full_result.get("blocked")`）→ AttributeError。

此外 `full_check` 的重复检测参数要求 `list[str]`，
而 `session.answer_history` 存的是含题目上下文的 dict 列表，类型不匹配。

### 2.3 配置导入错误

`session.py` 写的是 `from .. import config`（导入**模块**），
但轮次常量定义在 `Config` **类**里，正确应为 `from ..config import config`（导入实例）。
→ `config.INTERVIEW_ROUNDS` 抛 AttributeError。

### 2.4 前后端协议不一致

| 项目 | 前端 | 后端 | 后果 |
|------|------|------|------|
| 简历上传 | `/api/upload-resume` | `/api/sessions/upload` | 404 |
| 获取报告 | `/api/report/{id}` | `/api/reports/{id}` | 404 |
| WS 消息体 | `{type, ...data}` 展开到顶层 | 读 `msg.data.text` | 回答永远读到空串 |
| 回答字段 | `answer` | `text` | 同上 |
| 诊断结构 | 读 `data.diagnosis[key].score` | 返回 `dimension_details` | 四维度全显示 0 分 |
| 改写字段 | `data.rewrite` | `rewritten_answer` | 改写示范不显示 |
| 题号 | `data.index + 1` | 已是从 1 开始 | 题号多加 1 |
| 报告数据 | `data.report` | data 即报告本体 | 报告为 undefined |

## 三、技术方案

### 3.1 诊断维度权重按 JD 动态化

**新增** `backend/dimension_weights.py`

- `analyze_jd_weights(llm, jd)` → LLM 分析 JD，输出四维权重 + 理由
- `normalize_weights()` → 裁剪到 [0.10, 0.45] 并归一化到和为 1.0，防止某维被压到失效
- `weighted_score(dims, weights)` → 加权总分；跳过解析失败的 0 分维度，避免误拉低
- 任何异常路径（无 JD / 调用失败 / 返回非法）一律**退化为等权**，不阻断面试

**权重判断策略**（写入 Prompt）：
- 数据/算法/增长岗 → 量化程度权重高
- 架构/研发/攻坚岗 → 逻辑连贯性权重高
- 管理/项目/咨询岗 → STAR 完整度权重高
- JD 技能要求具体、门槛明确 → 岗位相关性权重高

**贯穿全链路**：
1. 权重注入 Diagnostician 系统提示词（高权重维度分析更细致）
2. 也注入 Rewriter（优先修补"低分且高权重"的维度）
3. `overall_score` 改为加权平均
4. 轮次推进判定、报告总分、雷达图综合分统一采用加权口径
5. 前端在面试区与报告页展示权重条

> **约束遵守**：诊断四维度本身**未做任何增删改**，只调整其权重，符合 CODEBUDDY.md 的"诊断四维度"不变量。

### 3.2 追问与诊断流式合并

**改造** `diagnosis_engine.py` + `main.py`

原流程（3 次 LLM 往返，追问需独立回合）：
```
诊断(非流式) → 弹出完整结果 → 判定追问 → 再调 LLM 生成追问 → 独立等待
```

新流程（2 次往返，追问零额外调用）：
```
Diagnostician(流式) ──► 逐字推送，同时产出 follow_up_question
        ↓
Rewriter(流式) ──────► 逐字推送改写
        ↓
diagnosis_done ─────► 标准化结果（含追问）→ 追问直接展示
```

- Diagnostician 输出 JSON 新增 `follow_up_question` 与 `weakest_dimension` 字段，
  低分时自动带出针对最弱维度的追问 → **省掉一次 LLM 调用**
- `run_diagnosis_streaming()` 此前已实现但从未被调用，本次接入 WebSocket 主流程
- 新增 `_astream()`：把 `chat_stream` 的**同步生成器**经队列桥接为异步生成器，
  避免阻塞事件循环导致其他会话卡死
- 前端新增 `diagnosis_status` / `diagnosis_chunk` / `rewrite_chunk` 消息处理，实时显示两个 Agent 的工作过程

> **约束遵守**：双 Agent 仍是两次**独立调用**、各自独立 Prompt，只是改为流式并串联推送，**没有合并为单一 Agent**。

### 3.3 雷达图实时更新

**新增** `frontend/js/liveRadar.js`

- 面试进行区挂载"实时能力雷达"卡片
- 每题诊断完成后，后端推送 `radar_update`（`session.radar_snapshot()`）
- 双数据集：**累计平均**（实线）+ **本题得分**（虚线），便于看出单题波动
- 复用已有 Chart.js 实例做 `chart.update()` **原地更新**，而非销毁重建，避免闪烁
  （week2 文档"已知限制"中提到的"Chart.js 重建可解决"，实测原地更新体验更好）
- 卡片下方渲染权重条，直观展示"这个岗位更看重哪一维"

### 3.4 弱项自动追加针对性题

**改造** `question_gen.py` + `session.py`

- `round_weak_dimension()` 定位薄弱维度，判据是**加权失分** `(5 - 均分) × 权重`
  —— 同样是 2.8 分，岗位更看重的维度会被优先补强
- `generate_round_questions()` 新增 `focus_dimension` 与 `weak_evidence` 参数
- 为四个维度各写了一套定向出题策略，例如：
  - 量化程度弱 → 逼问具体提升比例、耗时数值、如何测量得到
  - 逻辑连贯性弱 → 要求解释技术决策取舍、为何排除其他方案
- 把该维度的**具体失分评语**注入 Prompt，让补强题贴合真实短板，而非泛泛而问
- 明确要求"不要出现补强题之类的元信息，不要直接告诉候选人他哪里不好"，保持面试拟真感

### 3.5 其他修复

- `question_gen.py` 的 `chat_json` 是**同步阻塞**调用却在 async 函数中直接执行，
  会卡住整个事件循环 → 改用 `asyncio.to_thread`
- 追问环节新增 `skip_follow_up` 消息支持。
  原前端"跳过"发的消息后端不识别，会导致流程**永久卡死**
- `report.js` 使用了 `toast` 却未导入，且导入了不存在的 `getSession` → 修正

## 四、涉及的知识点

1. **加权评分模型**：权重归一化、区间裁剪、缺失值处理策略
2. **异步流式桥接**：同步生成器 → 异步生成器（`asyncio.Queue` + `run_coroutine_threadsafe`）
3. **事件循环阻塞**：`asyncio.to_thread` 处理同步 I/O，避免单个慢请求拖垮全部会话
4. **WebSocket 状态机**：多层嵌套循环下的消息分发、跳过/心跳等旁路消息处理
5. **Chart.js 增量更新**：`chart.update()` 原地刷新 vs 销毁重建的取舍
6. **LLM 输出鲁棒性**：markdown 围栏剥离、噪声前后缀容错、失败降级链路
7. **Prompt 工程**：权重注入、定向出题策略、失分证据注入

## 五、验证记录

因本地未安装第三方依赖，采用 **mock LLM 端到端仿真**验证（无需 API Key）。

### 5.1 权重模块单元验证

| 用例 | 输入 | 结果 |
|------|------|------|
| 极端值裁剪 | `{9, 0, -1, "x"}` | 归一化为 `{0.375, 0.208, 0.208, 0.208}`，和 = 1.0 |
| 空输入 | `None` | 退化等权 |
| 加权计分 | 量化权重 0.45 但得 1 分 | 2.3（等权时为 3.0）|
| 0 分跳过 | 仅一维有效 | 4.0（未被 0 分拉低）|

### 5.2 JSON 提取鲁棒性

| 输入 | 结果 |
|------|------|
| 纯 JSON | ✅ 解析成功 |
| markdown 围栏包裹 | ✅ 解析成功 |
| 前后有噪声文本 | ✅ 解析成功 |
| 无 JSON / 空串 | ✅ 返回 None，走降级 |

### 5.3 全流程仿真（拟真模式）

```
1. 权重: STAR 20% / 量化 45% / 逻辑 20% / 岗位 15%   source: llm
2. 题目数: 3
3. 流式类型: diagnosis_status / diagnosis_chunk / rewrite_chunk / diagnosis_done
4. 加权总分: 2.65   弱项: quantification   追问: 能给出具体提升比例吗？
5. 追问复用诊断产出（零额外 LLM 调用）
   追问补充后 round_answers 仍为 1（未被误计为新题）
6. 质量检查 / 7. 追加题定向 / 8. 实时雷达 / 9. 轮次推进 / 10. 报告加权
```

**关键验证点**：同一份回答，等权得 3.25 分，数据岗加权后得 2.65 分——
量化短板被正确放大，证明动态权重真实生效。

### 5.4 弱项追加题触发链路（技术广度轮）

```
质量: avg=1.55  passed=False  weak=量化程度  can_extra=True
弱项证据: 毫无数据支撑；毫无数据支撑
追加题 focus: quantification
定向 prompt 含量化策略: True
定向 prompt 含失分证据: True
```

## 六、已知限制（本次未解决）

1. 权重分析每场面试调用一次 LLM，若 JD 极短（< 8 字）直接退化等权
2. 流式诊断的 chunk 是**原始 JSON 文本**，前端展示的是模型"思考过程"而非格式化内容
3. 实时雷达只统计已完成的题目，追问补充的内容不单独计分
4. 弱项判定基于**本轮**数据，跨轮次的持续性弱项尚未累计追踪

## 修改记录

### [2026-07-31] 初版实施

- 原方案：直接在现有流程上叠加四个新功能
- 实施中发现的问题：v2.5 引擎拆分遗留了 6 处接口断裂 + 安全层返回值误用 + config 导入错误 + 8 处前后端协议不一致，WebSocket 面试流程实际处于**运行即崩溃**状态
- 修改后的方案：先做"第 0 步前置修复"打通全链路，再叠加四个深化功能。
  否则新功能无法验证，也无法确认是新代码的问题还是旧代码的问题

### [2026-07-31] JD 长度门槛调整

- 原方案：JD 少于 20 字符时退化等权
- 发现的问题：仿真中 `"数据分析岗，要求量化能力"`（12 字符）被误判为无效 JD，动态权重静默失效。中文信息密度远高于英文，20 字符门槛对中文过于严苛
- 修改后的方案：门槛降至 8 字符，并在代码注释中说明中文场景的判断依据

### [2026-07-31] 雷达图更新策略调整

- 原方案：按 week2 文档"已知限制"的提示，用 Chart.js **销毁重建**实现实时更新
- 发现的问题：每题重建会导致图表闪烁，且丢失动画连续性，反而不如不更新
- 修改后的方案：改为保留实例、`chart.update()` **原地更新数据**，并加入 400ms 过渡动画

### [2026-07-31] 追问计分口径修正

- 原方案：追问的补充回答按一次独立作答处理
- 发现的问题：这会让"一次追问 = 一道题"，扭曲轮次进度与平均分——回答越差、追问越多、题目数越膨胀
- 修改后的方案：追问补充**并入上一题**的回答语境（追加到原答案后），不新增题目计数

### [2026-07-31] 跳过追问导致流程卡死

- 原方案：前端"跳过"按钮发送 `skip_follow_up` 消息
- 发现的问题：后端追问环节只等待 `answer` 类型消息，收到 `skip_follow_up` 会**永久阻塞**。
  一度考虑让前端改发一条 `（跳过追问）` 的假回答绕过，但这会污染回答历史，还可能被安全层的质量校验拦截
- 修改后的方案：后端显式支持 `skip_follow_up` 与 `ping`，跳过时清空待推送追问并回执确认
