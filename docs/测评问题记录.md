## 问题 #1：追问机制与真实面试逻辑不符（跳过追问零成本）

- **发现时间**：2026-08-27
- **解决时间**：2026-08-30（v7.0.2，方案 C：跳过留痕）
- **发现场景**：模拟面试（simulation 模式）技术广度轮，回答框架对比题后触发面试官追问
- **状态**：✅ 已解决

### 现象

追问界面提供「提交补充」和「跳过追问」两个按钮，但：

1. 本题的五维评分、雷达图在**追问出现之前**就已经计算并落账（`main.py` 930-953 行：诊断 → `record_answer()` → 推送 `diagnosis_result` + `radar_update`，之后才生成追问）
2. 「提交补充」后补充内容只被拼入历史语境（`session.py` `handle_follow_up_answer()`：`round_answers` 追加 `[追问补充] ...`），**不会重新评分**——追问中再好的表现也不改分
3. 「跳过追问」只清空 `pending_follow_up` 并继续下一题（`main.py` 974-980 行），**无任何惩罚**

结论：跳过追问是恒最优策略（省时且零损失），追问机制对评分而言形同虚设。

### 与真实面试事实的差距

| 真实面试 | 当前系统 |
|---|---|
| 追问表现直接影响面试官评价 | 补充回答永不改分 |
| 回避追问本身就是负面信号 | 跳过追问零成本、零痕迹 |
| 追问是深挖能力的考察环节 | 追问只剩"让报告材料更全"一个软价值 |

### 当初的工程权衡（代码注释原文）

`session.py` 414 行：

> 追问补充不单独计为一道题，而是并入上一题的回答语境，避免"一次追问 = 一道题"扭曲轮次进度与均分。

另 v2.6 性能优化：追问由流式诊断**一次性顺带产出**（省一次 LLM 往返）。

### 候选改进方案

| 方案 | 做法 | 代价 | 评估 |
|---|---|---|---|
| A. 补充后重评 | 补充并入后重新诊断该题并替换分数 | 每次补充 +1 次 LLM 调用（10-20s），分数漂移导致轮次均分抖动 | 最"真实"但成本/稳定性差 |
| B. 追问独立记分 | 新增"追问应对"评分维度 | 改诊断维度结构 + 权重体系，改动大 | 过度设计 |
| **C. 跳过留痕（推荐，v7.0.2 已采纳）** | 跳过时在诊断记录上标记"追问回避"，综合报告如实提及（如"候选人对 X 追问未作展开"） | 约 20 行改动（`session.py` 标记字段 + `report.py` prompt 注入） | 零成本让"回避"事实可见，符合"报告是对面试的如实记录"定位 |

## 问题 #2：岗位描述（JD）不支持上传 PDF/TXT 文件解析

- **发现时间**：2026-08-27
- **解决时间**：2026-08-30（v7.0.2）
- **发现场景**：全链路测评，创建面试会话环节
- **状态**：✅ 已解决

### 现象

1. JD 仅支持在文本框手动粘贴；本地已有现成 JD 文件（如 `data/resumes/后端Python_张三_目标岗位JD.txt`）时，需手动打开 → 全选复制 → 粘贴，操作繁琐
2. PDF 格式的招聘 JD（招聘网站导出 / HR 发放的最常见格式）完全无法导入
3. 对照：简历侧已支持 PDF/TXT 双格式上传解析，两侧行为不对称

### 影响

- 长 JD（数千字）手动粘贴繁琐，易截断 / 格式错乱
- PDF JD 无法使用，降低真实求职场景可用性
- 与"模拟真实面试"的产品定位不符：真实用户拿到的 JD 通常是文件形态

### 实施情况（v7.0.2）

- 新端点 `POST /api/upload-jd`（`backend/main.py`）：复用 `resume_parser`（PDF/TXT/DOCX），与 `/api/sessions/upload` 同款限流 / 大小硬限制 / 扩展名白名单 / 413·400 处理
- 前端（`interview.js` + `api.js`）：JD 文本框上方新增"解析文件"控件，解析结果回填 textarea 并脱离岗位库关联
- 解析结果不入岗位库——与"临时上传即开练"的简历上传同一语义
