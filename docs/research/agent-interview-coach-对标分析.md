# agent-interview-coach 对标分析报告

> 研究对象：https://github.com/xiaodeng-lp/agent-interview-coach（微信面试教练，MIT，5 commits，本地优先）
> 分析目的：对标学习其设计亮点，找出可借鉴到「AI模拟面试官」的能力
> 分析日期：2026-08-28
> 结论依据：GitHub 仓库源码（app/engine.py、prompts.py、commands.py、interview_corpus.py、session_store.py、architecture.md 等）+ 自家 backend 横向代码审计

---

## 1. 项目概览

| 维度 | agent-interview-coach | 自家「AI模拟面试官」 |
|---|---|---|
| 定位 | 把微信变成 AI 面试官的本地化训练工具 | Web 端 AI 模拟面试 + 职业规划 + 市场数据分析 |
| 目标岗位 | 专攻 AI 应用 / Agent / RAG / MCP / LLM 工程岗 | 通用技术岗（含跨岗对比） |
| 技术栈 | Python 3.10+，OpenAI 兼容 API，wechat-clawbot，本地 JSON 持久化（零外部 DB） | Python 3.12 / FastAPI + WebSocket / SQLite (aiosqlite) / 多 AI 后端 / 原生 ES Module + Chart.js / Playwright |
| 依赖 | 仅 5 个（wechat-clawbot / openai / python-dotenv / python-docx / pypdf） | 多，含 Playwright、pytest 等 |
| 交互端 | 微信 + CLI 兜底 | Web 页面 + WebSocket 实时流式 |
| 评分 | 每轮 LLM 自评（四维，纯 Prompt 结构化输出） | 双 Agent（Diagnostician + Rewriter）流式五维加权（1-5 分） |
| 能力侧重 | 简历证据驱动的动态追问、多模式协议、薄弱点复盘 | 结构化诊断、职业规划时间轴、市场采集、多后端切换 |

**一句话总结**：该项目的护城河不在评分精度，而在**"像真实面试官一样盯着你的简历漏洞追问"**的交互设计与提示词工程；自家项目的护城河在**结构化双 Agent 诊断 + Web 实时流式 + 职业规划/市场数据生态**。两者互补性很强。

## 2. 架构解析

### 2.1 数据流（GitHub 项目）

```
微信 → wechat-clawbot(长轮询) → wechat_channel.py(消息/文件路由)
     → commands.py(命令路由) → materials.py(资料导入/刷新)
     → interview_corpus.py(语料构建+轻量RAG) → engine.py(面试提示词组装)
     → model_client.py(OpenAI 兼容 API) → 微信回复
```

### 2.2 模块职责对照

| GitHub 模块 | 职责 | 自家对应物（现状） | 差距 |
|---|---|---|---|
| `prompts.py` | 系统提示 / 四模式 / 四阶段 / 弱点标签 / 强制输出结构 | `diagnosis_engine.py` 内联双 Agent Prompt + `question_gen.py` | 缺"模式化提示"与"强制结构化输出" |
| `engine.py` | 提示词分层组装、模式冲突过滤、不会答恢复、证据硬规则 | `diagnosis_engine.run_diagnosis_streaming()` | 无证据注入、无恢复机制 |
| `commands.py` | 斜杠命令 + 语义意图识别（模式/阶段切换） | `main.py` WebSocket 路由 | 无运行中模式切换端点 |
| `interview_corpus.py` | 本地材料分块 + 关键词检索 + 上下文预算（轻量 RAG） | `resume_parser.py`（仅纯文本抽取） | **完全缺失** |
| `session_store.py` | 会话 / 评分 / 弱点 / 复盘 / 答案库 JSON 持久化 | `interview_engine/session.py` + `db.py` 的 `sessions`/`weakness_profile` 表 | 薄弱点缺 session 内跨轮累计；标准答案未沉淀 |
| `wechat_channel.py` | 微信长轮询 + 文件导入 + 回复 | —（Web 架构无微信端） | 不适用（低优先级可选） |

## 3. 核心设计深度解析

### 3.1 简历证据驱动的动态追问（最大亮点）

**证据包（Evidence Package）**：每次生成回复前，从简历语料库检索与用户本轮回答相关的片段，组装成 `【本轮证据包】`，格式含来源、片段编号、证据等级与正文。

**证据硬规则（`EVIDENCE_USE_HARD_RULES`）**：强制模型——
- 只能依据【本轮证据包】或用户亲述来生成经历/项目动作；
- 大模型常识仅用于解释概念，**禁止硬编经历**；
- 证据不足时必须**澄清追问**，而不是"顺着说"。

**设计价值**：这直接解决"AI 面试陪练只会顺着用户编"的问题。面试官"像读过简历一样"，能抓住简历与口述的矛盾点追问（漏洞追问），且不制造虚假经历。

### 3.2 四维/五维 LLM 自评分 + 强制结构化输出

**评分方式**：无任何数值/硬编码算法，评分完全由 LLM 依据 Prompt 自评，输出强制结构：

```
【反馈】（可信度/技术准确性/表达结构/风险点）
【评分】总分:xx 可信度:xx 技术准确性:xx 表达结构:xx 项目真实性:xx
【薄弱点】1-4 个短标签（如 MCP、RAG、项目真实性）
【更好的说法】模拟面试回答
【继续追问】仅一个问题
```

**设计价值**：
- 强制输出结构使程序解析极简（按标记切分即可），工程成本低；
- 自评维度针对"AI 工程岗"定制（可信度/项目真实性专治简历包装）；
- 与自家双 Agent 五维加权相比，**解析更简单但稳定性弱**——这是自家可以超越的点（后述）。

### 3.3 多阶段 × 多模式协议

- **4 阶段（STAGES）**：电话筛选面 → 技术一面 → 技术二面/主管面 → HR面，各有考察侧重。
- **4 模式（MODES）**：
  - 教练模式：先补基础再追问（教学优先，不输出分数）；
  - 技术面模式：标准技术面试官，追问项目细节、技术取舍；
  - 拷打模式：高压追问，优先抓名词堆砌、过度包装、真实性漏洞；
  - 只面试模式：只问不解析，每轮 ≤ 一句反馈 + 一个追问。
- **组合态**：`session.stage / session.mode` 组合透明展示（如"技术二面 / 拷打模式"）。
- **语义意图识别**：不仅支持 `/模式 拷打` 显式命令，还支持自然语言（"换拷打""改成教练"）与自动切换（用户卡住+求教 → 无声切教练模式）。

### 3.4 不会答恢复流程（Coaching Recovery）

检测用户"答不上来 / 不了解 / 没思路"等信号，注入 `COACHING_RECOVERY_INSTRUCTION`：
1. 讲清概念核心 → 2. 给出项目表达骨架 → 3. 提醒简历未支撑处"不要硬说" → 4. 只追一个降阶问题 → 5. 保留【薄弱点】记录。

**设计价值**：产品规则明确"用户明显不会时，系统应帮助其恢复，而非单纯加压"，这是对候选人的"教练感"来源，也是该项目的 AGENTS.md 核心产品规则。

### 3.5 轻量本地 RAG + 上下文预算

无向量库，零外部依赖的检索方案：
- 分块：`CHUNK_SIZE=2000`、`OVERLAP=250`、单文件截断 120k 字符；
- 文件名优先级启发式（协议 100 / 背景材料 98 / 终极简历 95 / PDF 55）；
- 评分：`score = chunk.priority + len(matched_terms) * 8`，仅在标题+前 800 字符内匹配；
- 上下文预算硬限：`max_chunks=4` / `max_chars=6000` / `max_chunks_per_source=2`；
- 输出诊断：`trace_retrieval` 支持检索溯源（哪块、什么词、为什么选中）。

**设计价值**：足够轻（单文档关键词打分 O(N·M)），契合"本地优先、隐私保护、零托管依赖"；预算硬限防止 token 膨胀。局限是召回精度受限于关键词，无法处理语义同义。

### 3.6 薄弱点累计 + 复盘 + 标准答案

- `WEAKNESS_KEYWORDS`（MCP/LangGraph/RAG/向量数据库/项目真实性…）作为弱点标签体系；
- 【薄弱点】随每轮输出累计到 `session`，`/今日弱点` 可查；
- `/复盘` 生成 Markdown 复盘（含薄弱点、改进建议）；
- `/标准答案` 将"更好的说法"沉淀为可背答案。

### 3.7 双端与工程纪律

- 微信 + CLI 双端（`cli_chat.py` 兜底），Windows 一键安装脚本 + `doctor.ps1` 全量诊断 + `smoke_test.py` 健康检查；
- AGENTS.md 明确工程纪律：本地优先、不引托管依赖、重材料真实性、严禁提交密钥/会话/真实材料，并附密钥扫描命令。

## 6. 风险与不适用点

1. **微信端对自家项目不适用（低优先级）**：自家为 Web + WebSocket 架构，微信桥接（wechat-clawbot）依赖第三方工具、有账号封禁风险，且与现有前端生态割裂。仅在方案中标注为可选扩展，不列入实施。
2. **纯 Prompt 自评的稳定性问题**：GitHub 的四维自评无结构化兜底，输出偶发格式漂移；自家双 Agent + 五维加权已更稳。**借鉴其"维度标签 + 强制结构"，但保留自家双 Agent 管线**，不要倒退。
3. **轻量 RAG 的召回精度局限**：关键词+优先级匹配无法处理语义同义（如"大模型"与"LLM"），对长简历召回可能漏项。可作为第一版落地，后续可按需评估 embedding 方案（注意自家"零托管依赖/本地优先"约束）。
4. **模式冲突过滤的复杂度**：GitHub 用"历史消息标记过滤"实现模式切换后的上下文一致性，逻辑较绕；自家若引入多模式，建议用"分模式会话窗口"或"模式标记 + 重建上下文"的简化实现。
5. **证据包 token 成本**：需严格沿用上下文预算（max_chars 上限），否则多轮后 token 膨胀。自家可结合现有 `llm_client` 的上下文窗口管理。

---

## 7. 结论

agent-interview-coach 的**差异化优势集中在"简历证据驱动 + 多模式协议 + 不会答恢复"的提示词工程层**，而这恰好是自家当前双 Agent 诊断管线（评分更强）之外最值得补齐的短板。最高杠杆的组合是：**把自家已有的强评分管线，接上对方"证据包 + 证据硬规则 + 不会答恢复 + 模式化提示"的交互骨架**，形成"又准又像真人面试官"的完整产品闭环。

详细改进方案见《agent-interview-coach-改进方案.md》。
