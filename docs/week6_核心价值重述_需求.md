# Week6 需求文档：核心价值重述（出题—诊断闭环）

> 日期：2026-08-13
> 性质：宪章级文案修正（无功能代码实现）
> 背景：用户用代码行数实量化，指出 CODEBUDDY.md 开篇"核心价值：回答质量诊断，不是'像不像面试官'"与实际资源分配矛盾，且"是 A 不是 B"的对立在架构上为假。

## 一、需求理解

宪章开篇句本意是与题库型 / 逼真型面试 App（参照 MockMate）做差异化定位。但它被同时当作"第一性原理 / 架构裁决标准"使用，要求所有版本取舍向"诊断"倾斜。用户质疑：该标准既未被真正执行，其"对立出题"的逻辑在架构上也不成立。

## 二、用户批判要点（[批判性思维]）

- 原声称"占开发精力 60%+"（week1）已被证伪。这是宪章自己打自己的抽烟枪。

### 2.2 "是 A 不是 B"在架构上为假（逻辑证据）

- `question_gen.py` 为每个诊断维度各写一套 `FOCUS_DIMENSION_PROMPTS`（"逼出具体数字""检验推理链条"）——开发者自己承认：要诊断好某维度，前提是问出能暴露该短板的问题。
- `generate_extra_question()` 用本轮薄弱维度反哺出题策略——诊断结果反向驱动出题。

二者构成相互定义上限的闭环，无法"重此轻彼"。

### 2.3 两类文本混用

产品定位语（面向用户/评审，允许简化）被原样搬成架构裁决标准（需能回答"该不该做、投入多少"）。按此标准，question_bank CRUD、web_research 岗位画像增强这类明显偏"出题基建"的模块理应被筛掉或精简，但实际完整存在 → 宪章未执行自己宣称的裁决标准。

## 三、原方案问题本质

"诊断，不是出题"是立项时为和 MockMate 类逼真模拟器做差异化而写的电梯演讲式定位语。它作为产品介绍合格，但被误升格为贯穿全程的架构裁决标准后：(1) 与真实资源分配（出题线更厚）直接矛盾；(2) 其"对立"表述在"出题质量卡诊断上限"的耦合架构面前不准确。本质是**营销话术与工程宪章的文本性质混淆**。

## 四、用户批判性判断点

- 判断依据：第一性原理应是"能回答资源分配"的可执行标准，而非口号；宪章若宣称某原则为最高裁决标准，就必须能筛掉与之冲突的模块，否则该原则失效。
- 取舍：承认出题是诊断的必要前置与质量杠杆，不否认出题价值，但要求文案诚实反映"出题服务于诊断闭环"，而非虚假对立。

## 五、修改后的文案

### CODEBUDDY.md 开篇

> 核心价值：诊断候选人的回答质量（STAR 完整性 / 量化程度 / 逻辑连贯性 / 岗位相关性 / 专业深度）。出题是本系统的必要前置与质量杠杆——问题围绕诊断维度设计，诊断结果反哺出题策略，二者构成"出题—诊断"闭环。我们与题库型 / 逼真型面试 App 的差异不在"不出题"，而在出题服务于诊断闭环、而非单纯生成逼真题面。

### week3 第一性原理

> 项目第一性原理：核心价值 = 诊断候选人的回答质量（五维）。出题是诊断质量的上限杠杆——问题围绕诊断维度设计、诊断结果反哺出题策略，二者构成"出题—诊断"闭环。本系统与题库型 / 逼真型面试 App 的差异不在"不出题"，而在出题服务于诊断闭环。
