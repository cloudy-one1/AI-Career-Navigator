> 来源：`https://github.com/crowscc/mock-interviewer`（MIT，2★，5 commits）

> 研读范围：`SKILL.md` + `references/` 三份参考文件（全文，约 12KB 中文，无一行程序代码）
> 研读日期：2026-08-28　对照基线：本项目 v6.2

## 0. 一句话结论

这是一个**把「面试方法论」从代码里剥离出来、全部沉淀为结构化 Markdown 知识资产**的项目。它没有一行代码，却在「面试官人格建模」「出题锚点工程」「教练模式」「评分 rubric」四件事上做得比多数有代码的项目更细。

**对我们的价值不在架构，而在内容层** —— `config.py` 里那 7 个面试官风格只有一段 `system_prompt`，而这里有 6 张**结构化的角色卡**（含「不会问」负向清单）、5 类**简历锚点提取规则**、5 种**追问范式**、15 道**压力题**、以及一套**带权重矩阵和加减分项的评分 rubric**。这些是可以「搬」的内容资产，不是要抄的架构。

## 1. 形态对比：这不是同类产品

| 维度 | mock-interviewer | 本项目 v6.2 |
|---|---|---|
| 形态 | Agent Skill（Markdown 技能包） | FastAPI Web 应用（前后端分离） |
| 运行时 | Claude Code / OpenClaw / Cursor 的 Agent 宿主 | 自有进程 `run.py`，端口 8000 |
| 状态管理 | 无状态机，靠 LLM 自觉 + 工作区 Markdown 文件 | `InterviewSession` Python 对象 + SQLite 持久化 |
| 持久化 | `mock-interview-YYYY-MM-DD.md` 单文件 | `interview.db`（会话/题目/诊断/报告） |
| 可控性 | 靠 Prompt 约束（软） | 轮次计数 + 收尾强控 + 输出净化（硬） |
| 可测试性 | 零测试 | 559 用例 pytest 套件 |
| 语音 | 无（纯文本对话） | MiMo 云端 TTS/ASR |
| 交互界面 | 宿主 CLI 对话框 | 自研 SPA + 图表 |
| 交付方式 | `npx skills add crowscc/mock-interviewer` | 源码部署 |

**判定**：领域同构，形态互补。它的**工程能力全面弱于我们**（无状态机、无持久化、无测试、无净化），但**内容资产的颗粒度显著细于我们**。借鉴策略应为：**取内容、弃架构**。

## 2. 架构解剖：渐进式披露（Progressive Disclosure）

### 2.1 文件结构

```
mock-interviewer/
├── SKILL.md                      # 主技能定义（流程控制 + 行为规则），约 3KB
└── references/
    ├── 面试官画像.md              # 6 种面试官的人格/视角/提问风格/追问模式
    ├── 出题策略.md                # 锚点提取、追问模式、JD 分析、压力题库、教练引导
    └── 评分标准.md                # 四维度评分细则、权重矩阵、level 对标、加减分项
```

### 2.2 三级加载机制（Agent Skills 标准的核心）

```
① 元数据常驻   → YAML frontmatter（name + description）始终在上下文，代价极小
② 触发后加载   → SKILL.md 全文进入上下文（含流程控制与行为规则）
③ 按需加载     → references/*.md 由 SKILL.md 显式指令「读取 XXX」时才加载
```

`SKILL.md` 末尾有一张**资源调度表**，把「哪个文件 / 什么用途 / 何时读」写死：

| 文件 | 用途 | 何时读取 |
|---|---|---|
| `references/面试官画像.md` | 6 种面试官的人格、视角、提问风格、追问模式 | 选完面试官后 |
| `references/出题策略.md` | 锚点提取规则、追问模式、压力题库、教练引导策略 | 面试循环中 |
| `references/评分标准.md` | 四维度评分细则、level 对标特征、加减分项 | 复盘时 |

**关键洞察**：它把**上下文窗口当作最稀缺的资源**来经营。选面试官时不加载评分标准，面试时不加载画像 —— 每个时刻只让模型看到「当下用得上的那一份规则」。

### 2.3 与我们 `knowledge_store.py` 的对照

我们 v6.0 已有命名空间知识库（`rag:interview` / `rag:career` / `rag:resume`），做的是**按域隔离**；它做的是**按时机加载**。两者正交，可叠加：

> 命名空间解决「检索哪片知识」，渐进式披露解决「这一刻注入多少知识」。

**可借鉴点（P2）**：`question_gen.py` 拼装 prompt 时，是否把「评分标准」「面试官画像」「市场上下文」一次性全塞进去了？若如此，可按生成阶段裁剪 —— 生成追问题时不注入评分 rubric，生成报告时不注入追问范式。

## 3. 触发层：把 `description` 当意图分类器写

它的 YAML `description` 长达 300+ 字，覆盖了**显式意图 + 隐式情绪 + 场景暗示**三层：

```
显式：「模拟面试」「面试练习」「帮我面一下」「mock interview」
情绪：「后天面试好紧张」「不知道怎么回答追问」「简历上写了XX但说不清」
场景：「只是分享了简历和 JD 想要匹配度诊断」
```

并显式写入一条**反向指令**：

> 不要等用户明确说"模拟面试"——任何暗示他们在准备面试、担心面试表现、想练习回答问题、或拿到了 JD 想针对性准备的场景都适用。

**评价**：这是 Agent Skill 的标准写法（description 就是唯一触发器，写窄了技能永远不触发）。我们不需要照搬（我们是显式按钮入口），但**「情绪化表达也应识别为面试需求」**这一条可下沉到前端 —— 例如在输入框 placeholder 或空态引导上，用「后天就要面试了，先练一轮」这类场景化文案承接焦虑用户，而非只有「开始面试」这种功能化文案。

## 4. 角色工程：6 张结构化面试官卡（本项目最大的内容差距）

### 4.1 角色卡 schema

每张卡固定 5 个字段，格式完全统一：

```
人格关键词 → 视角（一句话内心独白）→ 提问风格 → 追问模式（含轮数 + 链路图）→ 典型问法示例 → 【不会问】
```

### 4.2 六张卡一览

| 角色 | 人格关键词 | 视角（内心独白） | 追问链 | 轮数 | **不会问** |
|---|---|---|---|---|---|
| P7 技术面（同级工程师） | 较真、务实、代码级 | 这人来了能不能直接干活 | 表面描述 → 怎么实现 → 什么坑 → 怎么解决 | 1-2 | 宏观战略、组织管理、行业趋势 |
| P8 技术面（Tech Lead） | 全局观、方案思维、技术领导力 | 能不能独立做技术决策、带项目 | 方案 → 为什么选 → 对比过什么 → 重来呢 → 怎么推动 | 2-3 | 逐行代码实现、纯行业趋势 |
| P9 技术面（架构师） | 架构演进、技术战略、跨域 | 能不能做技术方向判断 | 架构 → 为什么 → 扩展性 → 扩新领域 → 行业更好做法 → 长期愿景 | 3+ | 代码、日常工程细节 |
| P8 业务面（业务负责人） | ROI 导向、数据敏感 | 懂不懂业务、能不能算清账 | 成果 → 数据口径 → 排除干扰 → 投入产出比 | 2-3 | 底层技术实现、代码质量、技术战略 |
| P9 业务面（总监） | 战略思维、组织能力、资源博弈 | 能不能做业务判断、建团队 | 决策 → 为何判断 → 依据 → 失败尝试 → 怎么调整 → 团队如何支撑 | 3+ | 技术实现、代码级问题 |
| VP/CTO 终面 | 格局、愿景、文化匹配 | 认知水平怎么样、能不能成核心骨干 | 开放观点 → 具体说说 → 什么支撑 → 如果你错了呢 | 2-3 | 任何技术细节、代码、架构 |

### 4.3 最值得抄的一点：**「不会问」负向清单**

六个角色**全部**显式声明了「不会问什么」。这是 Prompt 工程里被严重低估的手法 —— **正向描述模型会「创造性发挥」，负向清单才能划出硬边界**。

例如 P7 同级工程师不会问「宏观战略」，VP/CTO 不会问「任何具体技术细节」。没有这条约束，模型会让一个 P7 面试官聊行业趋势，角色立刻失真。

**对照我们的现状**（`config.py` `INTERVIEWER_STYLES`）：

```python
"strict": {
    "id": "strict",
    "name": "严格型",
    "description": "对候选人的回答追根问底...",
    "attack_level": 4,
    "interrupt_prob": 0.15,
    "system_prompt": "你是一位严格的技术面试官，追求深度和准确度。对候选人的回答要追根问底，不放过任何模糊表述。遇到不清晰的回答直接要求澄清，不接受敷衍。"
}
```

差距有三：

1. **无「视角」** —— 缺少「这个角色的内心独白」，模型不知道角色真正在评判什么。
2. **无「追问链」** —— 我们有 `should_follow_up` / `generate_follow_up`（薄弱维度驱动），但没有**绑定到角色的追问范式**。所有风格共用同一套追问逻辑，导致 7 种风格只在语气上不同，**提问结构上高度同构**。
3. **无「不会问」** —— 7 种风格没有任何负向边界。

> **P0 建议**：给 `INTERVIEWER_STYLES` 每个风格补 `perspective`（视角独白）、`followup_chain`（追问链，list[str]）、`never_ask`（不会问，list[str]）三个字段，在 `get_interviewer_system_prompt` 拼装时注入。这是**纯数据改动 + 一处拼装改动**，不动引擎逻辑，收益却是「7 种风格真正差异化」。

## 5. 出题引擎：三层锚点 + 动态追问 + 压力题

### 5.1 出题四层逻辑

| 层级 | 名称 | 来源 | 说明 |
|---|---|---|---|
| 1 | 简历锚点题（必问） | 简历 | 骨架：写了但没展开的关键信息点 |
| 2 | JD 锚点题（有 JD 时优先） | JD | 围绕简历与 JD 的 **gap 区域**出题 |
| 3 | 延伸追问（动态生成） | 候选人实际回答 | **面试的灵魂**：不是预设题目 |
| 4 | 压力题（随机插入） | 内置题库 | 模拟「突然被问懵」，插入 1-2 个 |

### 5.2 简历锚点五分类（最有价值的提取规则）

它把「可追问锚点」拆成**五类**，每类给了提取模式和追问方向：

| 锚点类型 | 识别特征 | 追问方向 |
|---|---|---|
| **技术选型** | 「用了 X」「基于 X 实现」「接入 X」 | 为什么用 X 不用 Y？原理？限制？踩坑？ |
| **量化数据** | 简历中**所有数字**都是高价值追问点 | 怎么测的？AB 还是前后对比？置信度？峰值？ |
| **架构设计** | 「搭建 X 系统」「从 0 到 1」「重构/升级」 | 整体架构？为什么这样？瓶颈？老架构什么问题？迁移怎么做？ |
| **业务决策** | 「主导 X 项目」「解决 X 问题」「贡献 X 指标」 | 为什么做？谁发起？优先级？归因？多少是自然增长？ |
| **团队管理** | 「带领 X 人团队」「协同 X 团队」「推广至全司」 | 怎么组建/分工/考核/招人？跨团队难点？推广阻力？ |

> 一句关键判断：「**简历中出现的所有数字都是高价值追问点**」—— 这条规则简单、可执行、命中率极高。

**对照我们的现状**：`question_gen.py` 的 `resume_points` 是 `deep` / `vague` 两分类（对标 GrillMind 的 `deepDivePoints` / `vaguePoints`）。二分法能定位「哪里值得问」，但**不能告诉模型「该往哪个方向问」**。

> **P0 建议**：`resume_retriever` 提取时把锚点打上五类标签（`tech_choice` / `metric` / `architecture` / `business_decision` / `team`），`question_gen` 在 `resume_points_block` 里按类分组注入，并给每类附一句追问方向提示。这样同一份简历，P7 优先取 `tech_choice` + `metric`，VP/CTO 优先取 `business_decision` + `team` —— **锚点的选用本身就实现了角色差异化**。

### 5.3 JD 锚点与出题优先级链

提取步骤：列出 JD 核心要求 5-8 条 → 逐条标注匹配度（**强匹配 / 弱匹配 / 无匹配**）→ **聚焦 gap 出题**。

优先级链写得很明确：

```
JD gap 区域（必问）> JD 强匹配区域（验证深度）> 简历锚点（补充探测）
```

并给了三类 JD 锚点的具体展开：硬性技能要求、软性能力要求、业务领域要求（含跨行业迁移探测）。

**对照**：我们有 `jd_text` + `gap_analyzer`（L2），但**出题时是否显式声明了这条优先级链**？`question_gen.py` 的 prompt 里若没有「优先问 gap，其次验证强匹配，最后才是简历锚点」这句指令，模型大概率会顺着简历走（因为简历内容在上下文里更「显眼」）。

> **P1 建议**：在 `generate_round_questions` 的 `extra_block` 中，把 `gap_analyzer` 产出的弱匹配/无匹配项作为**第一优先级指令**注入，格式如「本轮优先考察以下 JD gap：…」。

### 5.4 追问模式库（5 种范式，绑定角色）

| 范式 | 典型使用者 | 链路 |
|---|---|---|
| **漏斗式** | P7 技术面 | 用了某技术 → 核心原理怎么理解 → 实际遇到什么限制 → 怎么解决，有更好的办法吗 |
| **对比式** | P8 Tech Lead | 选了方案 A → 对比过 B 吗 → A/B 核心差异 → 什么条件下选 B → 现在重选呢 |
| **推演式** | P9 架构师 | 搭了 X 系统 → 用户量涨 10 倍哪里先扛不住 → 怎么改 → 改完下一个瓶颈在哪 |
| **质疑式** | 业务面 | 提升了 X% → 数据怎么算的 → 排除外部因素后呢 → 不做这个项目数字是多少 |
| **开放式** | VP/CTO | 你怎么看某方向 → 具体说说 → 有什么依据 → 如果你判断错了呢，Plan B |

**对照我们的现状**：`session.py` 的 `generate_follow_up` 是**薄弱维度驱动**的 —— 从诊断结果里挑最弱维度，取 `preset` 追问模板。这是「诊断驱动」，优点是精准，缺点是**所有面试官的追问长得一样**。

> **P0 建议**：把「追问范式」做成角色卡的一个字段（`followup_pattern`），`generate_follow_up` 拼 prompt 时**同时**注入「当前角色范式」+「本轮薄弱维度」。二者是正交的：薄弱维度决定**问什么**，角色范式决定**怎么问**。这个改动集中在 `generate_follow_up` 一个函数内。

### 5.5 压力题库（我们完全没有的能力）

5 类共 15 道，随机插入 1-2 个：

- **方案被否型**：精心设计的方案被上级否了怎么办 / 与另一团队方案冲突 / PM 要求简化
- **故障场景型**：系统挂了线上影响多大 / 大促延迟飙升怎么排查 / 上线后严重 bug
- **反转型**：不用你的方案会怎么做 / 换个人能做到一样效果吗 / 依赖服务涨价 10 倍方案还成立吗
- **竞品对比型**：壁垒是什么 / 头部公司做一样的产品怎么赢 / 有开源方案为什么自研
- **自我认知型**：最大技术短板 / 最失败的项目 / 团队成员怎么评价你

**对照**：我们的压力感来自 `attack_level` 和 `pressure` 风格，但那是**语气层面的压力**，题目本身仍在简历/JD 范围内。这里提供的是**内容层面的不可预测性** —— 真实面试的压力很大程度来自「被问到没准备过的东西」。

> **P1 建议**：新增 `backend/pressure_bank.py`（L2，纯数据，禁止依赖 L3/L4），按 5 类各存 3-5 道；`session.py` 在每轮按 `attack_level` 决定注入概率（如 pressure 风格每轮 1 道，friendly 风格 0 道），通过 `question_type_mix` 通道注入。注意：注入后要登记进 `asked_question_hashes`，避免与 `_is_duplicate_question` 冲突。

## 6. 教练模式：苏格拉底引导 + 卡点分类

### 6.1 机制

- **触发**：「提示」「help」「引导我」　**退出**：「继续」「回到面试」
- **核心红线**：**绝不给答案** —— 理由是「面试中没有人会给你答案，但好教练可以帮你学会怎么思考」
- **引导三层次**：定位卡点 → 拆解子问题（拆成 2-3 个可回答的小问题）→ 类比迁移（用候选人简历中其他经验做类比）

### 6.2 卡点分类 → 策略映射（这张表很实用）

| 卡点类型 | 策略 | 示例话术 |
|---|---|---|
| 不知道从哪切入 | 定位问题 | 「你是有想法但不知道从哪说起？」「这个问题核心在问什么，你觉得面试官想听什么？」 |
| 知道方向但说不清 | 提供结构 | 「试试分层：先结论，再理由，最后数据支撑」「按时间线：背景→你做了什么→结果」 |
| 技术细节记不清 | 类比迁移 | 「原理记不清没关系，你在实际项目中怎么用的？从使用经验反推原理」 |
| 业务数据答不上来 | 拆解估算 | 「精确数字记不住，那数量级呢？是几万还是几十万？」 |
| 被压力题打懵 | 回归第一性原理 | 「别急着回答，先想这个问题的本质在考察什么」「如果你是面试官，你想听到什么？」 |

### 6.3 两个工程化约束（值得抄）

1. **教练对话不计入该题评分**，但复盘中标注「借助引导」—— 保证评分公平性，同时不掩盖真实水平。
2. **同一场面试连续触发教练 3 次**，主动建议跳过当前方向，复盘中重点标注 —— **阈值化的主动干预**，避免候选人在一道题上耗尽信心。

**对照我们的现状**：我们有 `needs_recovery` / `recovery_active`（不会答恢复，v5.0）+ `generate_coach_tip`（教练提示）。但需要核实两点：

- 恢复态下的输出是否**真的不给答案**？若给的是「参考答案」而非「引导提问」，则与苏格拉底原则相悖，且会污染后续诊断。
- 是否有**触发次数阈值**？若无，候选人可以无限次触发恢复，把面试变成「提示驱动」。

> **P1 建议**（两条）：
> ① 在恢复/教练 prompt 中显式加入「禁止直接给出答案或参考答案，只能用提问引导」，并在 `output_sanitizer` 增加一条检测规则（若恢复态输出含「参考答案」「可以这样回答」等模式，触发改写或直接降级为纯引导话术）。
> ② 在 `session.py` 加 `recovery_count`，达 3 次时由工程层注入「建议跳过本题」的系统提示，并在 `record_answer` 的 tag 中标注 `assisted`，供 `build_report` 汇总。

## 7. 评分体系：四维度 + 权重矩阵 + level 对标 + 加减分项

### 7.1 四维度 5 分制（含行为锚定）

| 维度 | 5 分特征 | 3 分特征 | 1 分特征 |
|---|---|---|---|
| 技术深度 | 讲清演进历史、对比方案优劣、预判趋势 | 会用、懂原理，追问 2 层开始模糊 | 简历写了但不了解 / 明显背八股 |
| 表达结构 | 结论先行、分层清晰、能根据面试官反应调整 | 基本说清，偶尔发散或漏重点 | 逻辑不通 / 过度简短无有效信息 |
| 业务 sense | 从业务目标反推技术方案、算清 ROI、主动关联商业价值 | 知道业务背景，但技业关联不紧 | 纯技术视角，不关心业务目标 |
| 应变能力 | 压力下稳定、能拓展、能反问形成讨论 | 基本应对，偶尔慌或模糊 | 追问即崩 / 反复「不知道」零尝试 |

### 7.2 角色权重矩阵

| 面试官 | 技术深度 | 表达结构 | 业务 sense | 应变能力 |
|---|---|---|---|---|
| P7 技术面 | 40% | 20% | 15% | 25% |
| P8 技术面 | 30% | 25% | 20% | 25% |
| P9 技术面 | 25% | 25% | 25% | 25% |
| P8 业务面 | 15% | 25% | 40% | 20% |
| P9 业务面 | 10% | 25% | 40% | 25% |
| VP/CTO | 15% | 25% | 30% | 30% |

**对照**：我们有 `dimension_weights.py`（L2，可配置权重）+ `init_weights` / `dim_weights` / `weight_reason` / `weight_source`。**我们的实现更强** —— 权重是**动态推断**的（带理由和来源），而它的是**静态查表**。这一项不需要借鉴。

### 7.3 Level 对标（P7 / P8 / P9 回答特征）

对每个 level，逐一描述在**四个维度上**的回答特征。例如 P8 的「应变能力」：追问 2-3 层依然稳定 / 不确定处坦诚但给思考方向 / 能接住压力题给出有逻辑回答。P9 的：任何追问都能接住甚至反问形成讨论 / 对不确定问题给**分析框架而非具体答案** / 能把压力题转化为展示深度思考的机会。

**对照**：我们的 `diagnosis_engine` 打五维分数，但**是否给出了 level 对标**？`report.py` 若有「当前定位 + 差距分析」，可借鉴这套 P7/P8/P9 特征库作为**对标锚点文本**注入报告生成 prompt。

### 7.4 加减分项（最易落地、收益最直接的一块）

**扣分项**（分两级，不同严重度不同权重）：

| 扣分项 | 扣分 | 维度 |
|---|---|---|
| 假装知道（不懂装懂） | **-2** | 技术深度 |
| 夸大数据（经不起追问、前后矛盾） | **-2** | 业务 sense |
| 背诵感（明显背答案，追问就卡） | -1 | 技术深度 |
| 答非所问 | -1 | 表达结构 |
| 甩锅（「不是我负责的」「其他团队的问题」） | -1 | 应变能力 |
| 过度防御 | -1 | 应变能力 |
| 没有数据（成果描述全无量化） | -1 | 业务 sense |
| 全程被动（只回答不展开） | -1 | 表达结构 |

**加分项**：

| 加分项 | 加分 | 维度 |
|---|---|---|
| 主动延伸（答完补充相关思考） | +1 | 表达结构 |
| 坦诚不足（说清不了解并给学习方向） | +1 | 应变能力 |
| 反问面试官（形成技术讨论） | +1 | 应变能力 |
| 跨项目串联（展示系统性思维） | +1 | 业务 sense |
| 主动分享失败案例与反思 | +1 | 业务 sense |

**为什么值得抄**：这些是**可被工程检测的行为信号**，不完全依赖 LLM 主观判断。例如：

- 「没有数据」→ 正则检测回答中是否含数字/百分比 → 确定性触发
- 「过度简短 / 全程被动」→ 回答长度阈值 → 确定性触发
- 「假装知道」vs「坦诚不足」→ 检测「不知道/没接触过/不太了解」等标记，配合 `UNCERTAIN_ANSWER_MARKERS`（`session.py:39` 已有此常量）→ **我们已有基础设施**
- 「跨项目串联」→ 检测回答中是否提及简历里的其他项目名 → 可确定性检测

> **P1 建议**：在 `diagnosis_engine` 增加一层**规则化修正项（rule-based adjustment）**：先用确定性规则检测上述信号，生成 `adjustments: [{item, delta, dimension, evidence}]`，再与 LLM 评分合并。好处：① 评分可解释（每条修正都有 evidence 原文）；② 部分信号不依赖 LLM，稳定性更高；③ 报告可展示「为什么扣了这 1 分」，比纯分数更有说服力。
>
> 注意与 `dim_weights` 的作用点区分：权重管的是**维度间相对重要性**，修正项管的是**维度内的行为加减**，两者不冲突。

## 9. 不应照抄的部分（批判性审视）

### 9.1 无状态机是最致命的缺陷

它的流程是 `启动 → 读简历 → 选模式 → 选面试官 → 面试循环 → 复盘总评`，但**「面试循环」何时推进到下一环节、何时结束，完全由 LLM 自觉判断**。`SKILL.md` 只写了「完整模式环节顺序：自我介绍(1题) → 项目深挖(3-4题) → 技术原理(2-3题) → 系统设计(1题) → 行为面试(2题) → 反问环节」—— 这是**建议**不是**约束**。

后果：长会话必然出现环节漂移、题量失控、迟迟不进入复盘。**这正是我们在 v6.2 用 `CLOSING_INSTRUCTION` + 轮次计数解决掉的问题**（`config.py:369`：「使面试官在最后一轮自然收束，而不是无限追问（不依赖模型自决）」）。

> 结论：**我们已有的工程强控比它先进一档，不要因为它的内容细就反过来削弱我们的硬约束。**

### 9.2 其他不建议照搬的点

| 点 | 问题 | 我们的处理 |
|---|---|---|
| Markdown 单文件持久化 | 无并发安全、无原子写、进程中断易损坏 | 保持 SQLite |
| 评分全靠 LLM 自评 | 无 rubric 校准、无测试、不可复现 | 保持测试套件 + §7.4 规则化修正 |
| 「一次只问一个问题」 | 仅 Prompt 约束，无工程校验 | 可在 `output_sanitizer` 增加**多问号检测**（一句话里出现 ≥2 个「？」或「以及/另外/还有」连接的新问题时告警） |
| 无注入防护 | 简历/JD 文本直接进 Prompt | 保持 `security.py` 护栏 |
| 角色一致性 | 靠 Prompt 声明「保持角色一致，面试中不跳出身份做点评」 | 我们 `get_interviewer_system_prompt` 每轮重注入，更稳 |
| 教练模式与评分公平性 | 教练对话不计分但需人工标注 | 我们可用 `recovery_count` + `assisted` tag 自动化 |

## 11. 三句话总结

1. **它没有代码，但在「内容资产」上碾压我们** —— 6 张结构化角色卡、5 类锚点规则、5 种追问范式、15 道压力题、13 条加减分项，这些是我们 `config.py` 里那几段 `system_prompt` 远远比不了的。
2. **它的工程能力不如我们** —— 无状态机、无持久化、无测试、无净化、无注入防护。v6.2 的轮次强控、收尾强控、输出净化都比它先进，**不要倒退**。
3. **最值得今天就动手的两件事**：给 7 个面试官风格补「不会问」负向清单（半天工作量，效果立竿见影），以及给诊断加一层规则化加减分项（让评分第一次变得可解释）。
