## 一、模块目标与决策

### 1. 薄弱点 EMA 衰减 + 过期淘汰（`backend/weakness_memory.py`，L2）

**缺口**：v6.4 建成了长期记忆闭环（resolved 标记 + 首轮回注入），但闭环里跑的是 `_weakness_counts[t] += 1` 的**裸计数**——出现 3 次和 10 次一样重、答好了也不减、30 天前的短板和昨天同权重。

**借鉴点**：`internal/memory/service.go` 的 `updateWeakness`（<60 加重 / >85 减轻 / 中性不动）。

**三点改造（为什么不照抄）**：
1. 评分制换算：对方 0-100 分制，我们是五维 1-5 分 → 先映射为薄弱度 `(5-score)/4×100`，阈值换算为 **<3.0 加重 / >4.5 减轻 / 3.0–4.5 中性**；
2. **岗位权重放大**（对方没有的概念）：`weight/0.2` 夹 0.5–2.0 倍——岗位越看重的维度，同样失分越要命。这是本项目相对原设计的真正增量，复用 v2.6 已有的 JD 动态权重；
3. 主键：对方是 (user_id, tag)，我们无用户体系 → 按 dimension 单键。

**保留的原版语义**：中性区"连 last_seen 都不续期"——即"30 天没有再暴露严重短板就认为已改善、自然淘汰"，衰减靠时间而非练习次数。

**持久化分工**：`weakness_profile` = 历史流水（图谱/建议用），新增 `weakness_memory` = 当前状态（每维度一行）。纯计算在 L2，CRUD 在 L1（db.py），L1 不得反向依赖 L2，故编排逻辑放在 L2 的 `weakness_memory.py`（L2 可依赖 L1）。

**升级兼容**：新表为空（老库刚升级）时，回注入与建议接口**回退 v6.3 的 `list_unresolved_weaknesses` 口径**——否则升级后首场面试会静默丢掉记忆回注入。

### 2. 面试技能状态机（`backend/interview_skills.py`，L3）

**缺口**：既有 `switch_mode` 是**整场**设定（simulation/coach/hardcore/interview_only）且**没有结束条件**——coach 进去就一直 coach。缺一层"临时插入、有进入条件、有步骤、有完成条件、走完自动退回"的能力。

**借鉴点**：`internal/skill/skill.go` 的 7 方法接口 + `SkillRegistry` 优先级匹配。

**两点刻意不照抄**：
1. **触发方式**：原版靠纯关键词 `strings.Contains`（还穷举 `"和…的区别"`/`"和...区别"` 变体），在真实面试里会把"Redis 和 Memcached 我都不太熟"误判成触发。本项目**默认显式触发**（WS `skill` 消息 / 前端入口），`can_activate` 仅在自动匹配开启时参与；
2. **结束反馈**：原版完成只清 `ActiveSkill` 不告诉用户。本项目返回 `closing_message`，由工程层推送"已回到正式面试"。

**技能边界**：技能轮的"回答"（如测验选项 B）**不是面试作答**，打五维分没有意义 —— 因此技能轮**不进诊断**、单独维护 `skill_history`，结束时自动退回。这是与原版最大的行为差异（原版仍走普通 Chat 链路、照样计分）。

**内置 3 个技能**：`quick_quiz`（5 题即时判分，P80）、`concept_teach`（苏格拉底讲解，≤4 轮，P70）、`tech_compare`（5 维度对比，P50）。原版 4 个中的 `project_highlight` 未移植——与本项目 STAR 诊断 + `resume_anchors` 高度重合。

### 3. 动态难度调度器（`backend/difficulty.py`，L2）

**缺口**：出题难度恒定，答得好不会加码、答得差不会放水。

**借鉴点**：`internal/difficulty/scheduler.go` 的连续 N 次达标升档 / 失手降档。

**关键取舍：只抄"轮内难度自适应"，不抄"阶段推进"**。
对方的调度器同时决定难度与阶段（basic→experience→design）；本项目**阶段/轮次推进是 v6.2 落地的工程强控**（轮次计数 + closing 强控），若让难度信号反向决定阶段流转，等于把已收敛的可控性交回统计信号。因此本模块只回答"这道题出多难"。

**必须配套做的归因披露**：难度升降会改变出题分布，而评分标准是固定的——分数变低时分不清"他变差了"还是"难度升了一档"。所以：
- `trace` 逐题记录生效档位 → 报告 `difficulty` 字段披露；
- 变档时 WS 推送 `difficulty_change` 事件。

**信号源纪律**（对方最大的坑）：它苦于没有真实评分，只能用"回复长度"代理，导致整套调度是噪声（研读报告 §16.1）。我们直接用 `diagnosis_engine` 的加权总分；且**无效分数（None/0/非数字）一律忽略**——诊断失败不是"得了 0 分"，误记会把难度一路降到底档。

## 二、涉及的知识点

- EMA（指数移动平均）在"记忆强度"建模中的应用：α 决定收敛速度（α=0.4 时 10 次迭代残差 0.6%）
- 有状态技能（Skill）与无状态工具（Tool）、整场模式（Mode）三者的语义边界
- 调度器信号的**可归因性**：任何改变输入分布的自适应机制，都必须同时披露自身轨迹
- 分层纪律：L1(db) 与 L2(计算) 的依赖方向，编排逻辑放 L2 而非 L1
- 升级兼容：新表为空时的回退路径（避免功能静默丢失）
